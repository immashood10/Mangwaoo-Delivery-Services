# Project: Mangwaoo — Multi-Vendor Delivery Marketplace

## What this is today
A Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS 4 + Framer Motion marketing site for **Mangwaoo**, a Karachi-based delivery brand (fast food, groceries, dairy, medicine). It is currently a **static informational frontend only** — five pages (`/`, `/about`, `/services`, `/areas`, `/contact`), no backend.

Not yet present: database/ORM, auth, API routes (`app/api/`), payments, cart/checkout, vendor accounts, order tracking. All content is hardcoded in `lib/data.ts`.

## Structure
- `app/` — route segments: `about/`, `areas/`, `contact/`, `services/`, plus root `page.tsx`/`layout.tsx`/`globals.css`. Each route dir has its own `page.tsx` (+ `layout.tsx` where present).
- `components/` — presentational, animated (Framer Motion) sections: `Navbar`, `Hero`, `ServicesSection`, `WhyChooseUs`, `ServiceAreas`, `Testimonials`, `FutureVision`, `CTASection`, `Footer`, `WhatsAppButton`, `ScrollToTop`, `LocationAreaFilter`.
- `lib/data.ts` — single source of truth for content: `BRAND`, `SERVICES`, `SERVICE_AREAS` (5 Karachi areas w/ lat/lng + delivery radius), `WHY_CHOOSE_US`, `TESTIMONIALS`, `FUTURE_ROADMAP`, `STATS`. Update here first when changing displayed content rather than hardcoding text in components.
- `lib/utils.ts` — shared helpers (e.g. className merging).
- Brand colors live in `tailwind.config.ts` (`brand` palette: primary red `#9B0000`, secondary `#C1121F`, dark `#111111`).

## No browser storage — everything lives in the database
- The site is going live on its own domain, so **never use `localStorage`, `sessionStorage`, IndexedDB or client-set cookies** to remember anything. Persist it in Postgres through an API route instead.
- Logged-in data hangs off the account: the cart (`CartItem`, `/api/cart`), saved addresses (`Address`, `/api/addresses`), likes, favourites, notifications, and which stories they watched (`StoryView`, keyed `u:<user id>`).
- For a not-logged-in browser there is the `Visitor` table (`lib/visitor.ts`, `/api/visitor`): the browser holds only one opaque, httpOnly `mangwaoo_visitor` cookie (set by the server; the DB stores just its SHA-256 hash) and the row remembers whether the first-visit location question was answered and the last location shared. A guest's watched stories are recorded against the same visitor id (`StoryView`, keyed `v:<visitor id>`). Guests have no cart and no saved-address list (adding to cart and ordering need a login).
- React state is fine for things that only need to last as long as the page. The WhatsApp code screen's `ticket` (below) is exactly that: it lives in React state, never in storage.

## Security rules (keep them when adding features)
- **Nothing in the browser**: no localStorage/sessionStorage/IndexedDB/cache storage/`document.cookie` — ESLint (`no-restricted-globals`/`-properties` in `eslint.config.mjs`) fails the build tooling if code uses them. Cookies are set by the server only (httpOnly).
- **Headers** (`next.config.ts`): no framing (`X-Frame-Options: DENY`, CSP `frame-ancestors 'none'`), nosniff, Referrer-Policy, Permissions-Policy (only geolocation + microphone), COOP, HSTS, and a Content-Security-Policy on the live site (scripts/styles `'self' 'unsafe-inline'` because Next inlines its bootstrap; images `self data: blob:`; `connect-src` also OpenStreetMap Nominatim; `frame-src` Google Maps). A new third-party script, image host, API or embed must be added to that policy or the browser blocks it.
- **CSRF guard** (`proxy.ts`): any non-GET request to `/api/*` that a browser says came from another site (`Sec-Fetch-Site` / `Origin`) gets 403. The session cookie is also `SameSite=Lax`.
- **Request limits** (`lib/rate-limit.ts`, table `RateLimit`, keys are hashes): login (10 per account / 40 per network address per 10 min), signup (10/h per address), forgot/reset password, contact form (5/h), password change, orders, chat messages, ad requests, order chats, plus the WhatsApp code limits. New routes that send messages, cost money or create rows for strangers need one: `enforceRateLimits([...])` returns the 429 response or null.
- **Passwords** (`lib/password-policy.ts`): at least 8 characters, at most 72 bytes (bcrypt), no common/repeated passwords, not the email. bcrypt cost 12; `verifyPasswordOrDummy` keeps "no such account" and "wrong password" identical in answer and time. Changing or resetting a password sets `User.sessionsValidFrom`, which voids every older login cookie (checked in `getSession()` through the 15-second list in `lib/bans.ts`); the browser that changed it gets a fresh cookie.
- **Sessions**: JWT (HS256 only, algorithm pinned) in an httpOnly, SameSite=Lax, Secure (live) cookie; `AUTH_SECRET` must be a long random value. Banned/deleted accounts are logged out within seconds (see Admin Users).
- **Uploads**: seller photos must be raster `data:image/(jpeg|png|webp|gif|avif);base64` (`isRasterImageDataUrl`), never SVG/HTML; chat attachments are allow-listed types served with `nosniff` and a sandbox CSP. Links in WhatsApp messages (password reset) use `siteOrigin()` (`SITE_URL`), never the request's Host header.
- **Dependencies**: `npm audit --omit=dev` must stay at 0 (Next 16.4.2, Prisma 7.10.1 at the last check). On this Windows PC the new Next's native SWC binary is blocked by an Application Control policy, so local dev/build use webpack (`npm run dev` = `next dev --webpack`; Vercel builds with the default and is unaffected).
- `.claude/` and `.kilo/` are not in the repository (the repo is public).

## Firebase (project `mangwaoo-delivery-service`)
- **Phone OTP through Firebase** (`PHONE_VERIFICATION_PROVIDER=firebase`; default is still WhatsApp): the code screen (`components/WhatsAppCodeForm.tsx`) asks Firebase Phone Auth to text the number (`lib/firebase-client.ts`: only `@firebase/app` + `@firebase/auth`, in-memory persistence, IndexedDB hidden from Firebase so nothing is stored in the browser; Google's reCAPTCHA runs invisibly), and sends the server the Firebase ID token. `lib/firebase-phone.ts` checks it with Google's public keys (RS256, issuer/audience = our project, `sign_in_provider` phone, signed in within 10 minutes) and `verifyFirebaseToken()` in `lib/phone-verification.ts` requires the token's number to equal the ticket's number, then confirms the account exactly like a WhatsApp code (same ticket, 5 tries, 60 s cooldown, rate limits). - **Planned, not done yet** (the owner asked for all of these): Cloud Storage for images (Firestore documents are limited to 1 MiB, the product photos are data URLs), the whole database on Firestore (replacing Prisma/Postgres, server-side Admin SDK only, rules deny all browser access), Firebase App Hosting instead of Vercel, push notifications (FCM; needs a service worker and IndexedDB in the browser, so it is an explicit exception to "nothing in the browser" and waits for the owner's OK). Needs the Firebase CLI login (`npx firebase-tools login`) and a service account for the server.

## Push notifications (Web Push, free)
- Every notification saved by `lib/notify.ts` is also pushed to the account's devices (`lib/push.ts`, `web-push`, signed with the site's VAPID key; no Firebase key needed). `PushToggle` (inside every notification bell: admin, seller, customer/rider) asks permission, registers `public/push-sw.js` (shows the notification and opens the page; caches nothing) and `POST /api/push/subscribe` stores the device in `PushSubscription` (only push-service hosts are accepted as endpoints; dead devices are dropped; deleted/banned accounts get nothing; logout removes the device). The browser itself keeps the permission and subscription, the site's own code stores nothing — the one deliberate exception to "nothing in the browser" the owner accepted.
- Needs on the host: `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` (secret), `VAPID_SUBJECT` (a web address). Without them the toggle hides itself and nothing is sent. Migration `20261024100000_push_subscriptions` must be applied.
- **Database:** moved on 2026-10-22 from Prisma Postgres (free plan ran out, "planLimitReached") to the owner's own Supabase Postgres (free, project `swcdmvlgamesqehmruiu`, Singapore). Supabase's direct host is IPv6-only, so always use the **pooler**: local `.env` and `prisma migrate` use the session pooler (`aws-0-ap-southeast-1.pooler.supabase.com:5432`, user `postgres.<project ref>`), Vercel uses the transaction pooler (same host, port `6543`) so serverless instances don't exhaust connections. The URL ends `?uselibpqcompat=true&sslmode=require` (plain `sslmode=require` makes node-pg verify Supabase's certificate and fail). The old data stayed in the blocked Prisma database. Keep polling light and avoid the big e2e suites against the live database.

## Order chats: "End chat" cancels the order (customer and rider)
- Both the customer (the "Chat with Rider" modal, `components/OrderChat.tsx`) and the rider who took the order (the bar above the chat in `/rider/chats`, `OrderActions` in `components/rider/RiderPages.tsx`) have **End chat**. It first asks (`components/ConfirmDialog.tsx`: "Are you sure you want to end this chat?", buttons **Cancel** (goes back, has the focus) and **Confirm**, and below them the small line "Order will be cancelled and chats will disappear."), then `POST /api/rider-chats/[id]/cancel`.
- Cancelling really deletes: `cancelOrderChat()` (`lib/rider-chat-cancel.ts`) locks the chat row (`FOR UPDATE`) and deletes its messages, photos/voice notes and the chat itself, for both sides. Only a chat that is still going (OPEN or ACTIVE) can be cancelled: a completed one (CLOSED, already charged) answers 409, and if a rider completes and the customer cancels at the same moment exactly one of them wins. No commission is charged. Only the customer who owns the chat and the rider who took it may cancel (a rider only looking at an open request can't); admins use **Delete** in Admin > Order Chats (cancel answers 403 for them).
- The other side is told with a notification that has NO page link (`href` null, so it shows in full and the bell counts it): the rider gets "Order cancelled", the customer "Your order was cancelled" (+ the admins "Rider cancelled an order" when a rider backs out after taking it). A chat that disappears under someone who is looking at it shows a notice (`onMissing`); `RiderShell.dropChat` removes a cancelled chat from the lists at once and ignores late polls.
- Delivered orders end through `POST /api/rider-chats/[id]/close`: the rider's **Complete order** and the customer's **Order received** (shown in the green banner while a rider is on the order, with its own Cancel/Confirm question). Only these charge the rider's commission; an admin's Close doesn't. The post-checkout page `/finding-rider/[id]` has no End chat (its food orders are cancelled from My Orders); a removed chat there says it was "cancelled or removed".
- Navbar on phones (`components/Navbar.tsx`): the right-hand group stays on ONE row from 360 px up (favourites, cart, Login, Sign up, **Chat** next to them; logged in: favourites, cart, bell, account, Chat): paddings shrink, the account's first name shows from 400 px and the button reads "Chat with Rider" from 480 px, "Chat" below that.

## Rider wallet: Mangwaoo's commission on every finished order
- **The rule** (owner's request, 2026-10-26): Mangwaoo keeps a percentage (**30 %**, `RiderWalletSettings.commissionPercent`) of the delivery charge of every order a rider finishes. A rider may leave **5** finished orders unpaid (`ordersOnCredit`); at 5 unpaid orders the rider is **not eligible for the next order** (can't go online, gets no requests, can't claim one) until everything owed is paid. Both numbers are editable by the admin (Rider Wallets > The rule) and apply to orders finished from then on; lowering the limit puts riders on hold, raising it releases those below it. 0 = pay before every next order. The owner's "5 orders" was an example, so keep both configurable.
- **What an "order" is**: a rider's order chat (`RiderChat`). It counts as DELIVERED when the rider presses **Complete order** (their chat panel, the charge is already filled in) or the customer presses **Order received** (their chat): both call `POST /api/rider-chats/[id]/close` → `closeOrderChat()` (`lib/rider-wallet.ts`), which closes a chat the rider claimed (ACTIVE) and writes ONE `RiderLedgerEntry` COMMISSION line (`chatId` is unique, so pressing it twice or from both sides at once charges once; tested with 6 simultaneous closes). An admin's **Close** only closes the chat (no commission: use Rider Wallets > Adjust if one is due), closing a chat nobody claimed charges nothing, and **End chat is NOT delivery**: it cancels the order (see "Order chats: End chat" below), so nothing is charged.
- **The base amount** (changed 2026-10-25, owner's request: the rider no longer types it): the **delivery charge of the order**, saved by the server. `POST /api/checkout` opens the rider's order chat itself (the cart page sends only the summary text, `chat: { addressText, pickupText, body }`) and stores the delivery fee it just priced (`quote.delivery`, the food delivery fees; 0 for MangwaooMart or sample items) in `RiderChat.deliveryCharge` (whole PKR, migration `20261029100000_rider_chat_delivery_charge`); a second checkout that joins the live chat adds its fee (`startOrContinueOrderChat`, `lib/order-chat.ts`, also used by `POST /api/rider-chats`). `deliveryChargeForChat()` (`lib/rider-wallet-config.ts`) is the one function that answers "what is this chat's charge": `deliveryCharge` when set, else (a chat not from a checkout, e.g. the customer's own request with a pickup point) the delivery rate for the pickup → drop-off distance (`minimumFeeForChat`, Rs 70/km); no pickup point and no saved charge = 0 = not charged. `serializeRiderChat` puts it on every chat as `deliveryCharge`, the rider's Complete order panel shows it read-only, and `closeOrderChat` charges the percent of the same number (rounded up to whole PKR). `POST /api/rider-chats/[id]/close` no longer reads anything the rider sends. Chats opened BEFORE this change have `deliveryCharge` null and no pickup point, so they count as 0 (no commission) when completed. If the owner wants a different base (e.g. the whole order value), change `startOrContinueOrderChat`'s caller in `/api/checkout` and `deliveryChargeForChat`.
- **Money lines** (`RiderLedgerEntry.amount`, PKR from the rider's side): COMMISSION negative, TOP_UP positive, ADJUSTMENT either way. `Rider.walletBalance` (negative = owes), `unpaidOrders` (commission lines not yet covered by payments, oldest first), `paymentHold` and `orderAccess` (AUTO | ALLOWED | BLOCKED, the admin's override) are kept in step with the ledger by `recomputeWallet()` inside the SAME transaction that locks the rider row (`FOR UPDATE`) and writes the line; never change them elsewhere. The hold starts when unpaid orders reach the limit and lasts until the balance is back to 0 or more. A hold also sends the rider offline.
- **Eligibility** = approved && `riderHold()` null (`lib/rider-wallet-config.ts`: BLOCKED → admin hold, ALLOWED → eligible, AUTO → not `paymentHold`). Enforced in `getOnlineRiders()` (`lib/rider-dispatch.ts`: nobody on hold is offered or can claim requests), `resolveRiderChatAccess` (a clear "Please recharge your account" refusal), `POST /api/rider/presence` (403 with `hold`) and the dashboard poll (`GET /api/rider/chats` also returns `wallet`). A rider on hold can still finish the orders they already hold.
- **Paying**: the rider sends the money to the owner's **EasyPaisa 03122855881 (Muhammad Mashood Khan)** (`AD_PAYMENT` in `lib/ad-config.ts`, also what sellers see for ads) and fills **Wallet** (`/rider/wallet`: `POST /api/rider/wallet`, multipart or JSON: amount, method, transaction id and an OPTIONAL **screenshot** of the payment; max 3 pending, a transaction id can't be reused unless it was rejected). The screenshot is shrunk in the browser (`compressImage`), its type is taken from its bytes (`lib/image-signature.ts`: JPEG/PNG/WebP only, never SVG, max 3 MB), stored in `RiderTopUpScreenshot` (its own table, so lists never load it) and shown to admins only (`GET /api/admin/rider-top-ups/[id]/screenshot`, `nosniff`, sandbox CSP, never cached; it stays after approval as a record). The admin checks it in **Rider Wallets** (`/admin/rider-wallets`, sidebar: "View screenshot") and approves (may correct the amount) or rejects (`PATCH /api/admin/rider-top-ups/[id]`), or records money received outside the app (`POST /api/admin/rider-wallets/[riderId]` `{action:'payment'|'adjust'|'access'|'remind'}`; adjustments need a reason). The admin page lists riders on hold first, with filters, the rule form, pending recharges, per-rider History, Send reminder and the Automatic / Always allowed / Block switch. Seller ad payments do not have a screenshot yet (only a transaction id).
- **Notifications** (rider bell, `href` `/rider/wallet`): "Please recharge your account" (automatically when the hold starts, and from the admin's reminder button; folded by `refId rider-recharge:<id>`), recharge approved / not accepted, payment added, adjustment, blocked / allowed, and "You can receive orders again". Admins get "Rider needs to recharge" and "Rider recharge waiting" (`ADMIN_PAGES.riderWallets`). Tests that exercise this write to the real admin's bell: delete notifications mentioning the test rider afterwards.
- Rider screens: dashboard banner + wallet card, sidebar **Wallet** link with a "!" while on hold, Complete order panel (`components/rider/RiderPages.tsx`), wallet page (`components/rider/RiderWallet.tsx`). Existing riders start at balance 0, AUTO.

## Rider face photo (required at signup, added 2026-10-25)
- Besides the two CNIC photos, a rider must give a clear photo of their **face** (`RiderDocumentKind.FACE`, migration `20261030100000_rider_face_photo`). The signup form (`/rider/signup`) uses `components/FaceCapture.tsx`: "Take a selfie" is a file input with `capture="user"` (the phone's own front camera) and "Choose photo" picks from the gallery; the browser shrinks it (`compressImage`) and it stays in memory until the form is sent. `POST /api/auth/rider-signup` refuses a signup without it. - Photos are judged by their bytes (`lib/rider-photo-upload.ts` → `detectRasterImage`: JPEG/PNG/WebP only, max 3 MB), never by the name or the type the browser claims. Riders who signed up before the rule have no face photo: unapproved ones get an "Add your face photo" card on their dashboard (`RiderFacePhotoCard`, `POST /api/rider/face-photo`, only while none is on file, so an approved face can't be swapped; to change it the rider asks Support). Approved riders without one are not asked.

## Automatic CNIC photo check by AI (added 2026-10-27, needs an Anthropic key)
- **What:** `POST /api/auth/rider-signup` reads the photos, then (before any account is made or code sent) `checkRiderCnicPhotos()` (`lib/cnic-check.ts`) shows the front and the back CNIC photo to Claude, both at once, through the official `@anthropic-ai/sdk`. Claude answers in a fixed JSON shape (structured output, `output_config.format`): `verdict` `cnic | not_cnic | unclear`, `side` `front | back | both | unknown`, and a few words in `shows`. The route refuses with 400 `{ error, fields: ['cnicFront'|'cnicBack'] }` only when a photo is **clearly not a CNIC** (`not_cnic`) or **clearly the other side** (a `cnic` whose `side` is the opposite one; `both` = one scan of the two sides and `unknown` fit either slot). `unclear` (a blurry card) is let through on purpose: the admin still looks at every photo, and a wrong refusal locks out an honest rider. The face photo is NOT checked, and the CNIC number the rider typed is not compared with the card.
- **Switch:** `ANTHROPIC_API_KEY` on the host (a secret; add it in Vercel and deploy again). No key = the check is off and signup is exactly as before (`cnicCheckEnabled()` in `lib/cnic-check-config.ts`, which has no SDK import so server pages can use it). `CNIC_CHECK_MODEL` picks the model (default `claude-opus-5-5` at `effort: low`, about a cent or two per signup; `claude-haiku-5-5` is much cheaper and quicker; the same request fits both). `ANTHROPIC_BASE_URL` (read by the SDK) points tests at a stand-in server. There is deliberately no refusal fallback: if Claude's safety rules decline (`stop_reason: refusal`), that counts as "could not check".
- **When it can't run** (no credit, bad key, Anthropic down, 20 s timeout after one retry, an unreadable answer) the signup is NOT blocked: it goes ahead unchecked, the reason is written to the server log (`[cnic-check] …`, never the key or a picture) and the admins get one folded bell notice "Automatic CNIC check is not working" (`refId cnic-check-unavailable`). `export const maxDuration = 60` on the route leaves room for the slow case.
- **The form:** `app/rider/signup/page.tsx` is now a tiny server page that passes `photoCheck={cnicCheckEnabled()}` to the client form `components/RiderSignupForm.tsx` (the old page body). With the check on, the form says an AI checks the two photos and the button reads "Checking your photos…". Photos named in `fields` are taken out of the form and `CnicCapture` shows its `problem` text under an empty red slot until a new photo is added.
- **Admin:** Rider Approvals (`CnicCheckStatus`) shows whether the check is on and the model, with a **Test it** button (`POST /api/admin/cnic-check`, admin only, 20 an hour each) that shows Claude a tiny grey square and reports "Working: … answered in 3 s" or why not (key refused, no credit, unknown model…). Use it after setting or changing the key.
- **Privacy:** the two CNIC pictures are sent to Anthropic's API for the check. The site's "Privacy Policy" link still goes nowhere (`#`), so nothing there mentions it yet.

## Rider order history, ratings and complaints (added 2026-10-25)
- **History** (`/rider/history`, sidebar "Order history", `GET /api/rider/history?filter=all|delivered|cancelled|pending&range=today|7d|30d|all&cursor=`; the dashboard shows a small "Your orders" summary with `?summary=1`): delivered / cancelled / pending counts, the delivery charges of delivered orders and Mangwaoo's share, the rider's rating, and every order newest first. ## Notification sound (added 2026-10-25)
- Every notification comes with a short chime (two notes, about 1.4 s, made with the Web Audio API in `lib/notification-sound.ts`: no sound file, nothing kept in the browser). `SellerNotificationsProvider` plays it when a poll brings a notification it has not seen, and that one provider is the bell of the admin, the seller, the customer and the rider. - **Browser rule:** a page may only make sound after the visitor has tapped, clicked or pressed a key on it once (`enableNotificationSound` listens for that first gesture and creates/wakes the audio context). Before it, or after a reload until the first tap, a notification is silent (the bell and the pop-up still show). Whatever was already waiting when a page loaded (a customer's or rider's first load) pops up but does not chime. Two chimes within 1.5 s collapse into one (two bells on one page, several notifications in one poll).
- Polling stops while the tab is hidden, so with the site closed or the phone locked only the **web push** notification (`public/push-sw.js`: `silent: false`, vibration, `renotify` for tagged ones) can make a sound, and it is the phone's/computer's own notification sound, which a web page cannot choose. No mute switch exists (it would have to live in the database, not the browser).

## Food delivery fee and coupons (checkout)
- **Only food has a delivery fee.** It is a flat rate per kilometre of the ride from the restaurant to the customer's location: `lib/delivery.ts` (`DELIVERY_RATE_PER_KM` = Rs 70 per km since 2026-10-25, before that Rs 10 = the bike's petrol; distance worked in 0.1 km and the fee rounded up to whole PKR; straight-line distance, `Seller.latitude/longitude` → the delivery address). MangwaooMart orders never get one, and no screen may show a delivery fee for them. A restaurant without a map pin has no fee yet (`deliveryNote: 'NO_RESTAURANT_PIN'`, shown as "To be confirmed"), never a silent "free". Home restaurant cards, the restaurant page and search results show the fee next to the distance once the customer's address is known.
- **One calculation, on the server.** `lib/checkout.ts` `priceCheckout()` prices a cart (items from the DB, food delivery, coupon); `POST /api/checkout/quote` shows it in the cart and `POST /api/checkout` places the whole cart (MangwaooMart + food, one order per seller) in ONE transaction with the same numbers. `/api/orders` and `/api/gulplaza-orders` are thin wrappers over `placeOrders` (no coupon). The browser never sends an amount. The built-in sample items (`MART_PRODUCTS` in `lib/data.ts`, no database row; shown on `/mart` and the home page while sellers have listed nothing) are priced from that catalog by `sampleOrders()` (one `quote.orders` entry per vendor, `sellerId` `sample:<vendor>`, always AFTER the real orders so `quote.orders[i]` stays `groups[i]`; no coupon, no delivery) but never stored as orders: the owner is told by WhatsApp and the customer still gets the normal success. Without this the cart showed PKR 0 for them.
- **Orders keep the items total in `totalAmount`** (what the seller earns) plus `discountAmount` and (food) `deliveryFee`; the customer pays `totalAmount − discountAmount + deliveryFee` (that is `Payment.amount`). Coupons are paid by Mangwaoo, not the seller.
- **Coupons** (`Coupon`, admin at `/admin/discounts`, sidebar "Discount"): code (stored in capitals), Discount %, optional max discount, minimum order, applies to (ALL / FOOD / MART), usage limit, valid-until day (Karachi time), one use per customer, active, note. The customer enters the code in the cart before Place Order. It takes the % off the items it applies to (never delivery), shared between the orders by their items. `CouponRedemption` is one row per checkout that used it; `releaseCouponIfUnused()` (`lib/coupons.ts`) gives the use back when every order of that checkout is cancelled (customer or seller routes). A checkout locks the coupon row (`FOR UPDATE`) so "once per customer" and the usage limit hold under double clicks. A used coupon can't be renamed or deleted, only paused.

- Anyone can therefore sign up with any phone number: no protection against fake accounts or someone else's number. Mention this if asked about abuse.

## WhatsApp verification (login needs a confirmed number — only when `PHONE_VERIFICATION_REQUIRED=true`)
- Every new customer, seller and rider is created **unverified** (`User.phoneVerifiedAt` null) and gets **no session** at signup. A 6-digit code goes to the WhatsApp number they entered; only after they type it (`POST /api/auth/verify-code`) is the number confirmed and the session created. `/api/auth/login` refuses an unverified account (403 + a fresh code and ticket, so the log-in screens switch to the code screen). The admin account is exempt (`canLogIn()` in `lib/phone-verification.ts`); accounts that existed before the feature were marked confirmed by its migration.
- Logic is all in `lib/phone-verification.ts`; the shared screen is `components/WhatsAppCodeForm.tsx` (used by `/signup`, `/sell`, `/login`, `SignInModal`, and Settings for a number change). Numbers must be Pakistani mobiles (`lib/phone.ts`, stored as `03001234567`).
- The DB keeps only hashes: `PhoneVerification` (ticket hash + keyed code hash, 10-minute expiry, 5 wrong tries, one row per account) and `PhoneVerificationSend` (send log: one code a minute and 5 an hour per number, 20 an hour per network, so the WhatsApp bill and strangers' phones are protected; it outlives the account on purpose).
- An unverified account is just an unfinished signup: signing up again with the same email/number replaces it (so a typo never locks an email out), admin lists/approvals ignore it, and forgot-password sends it nothing. A customer changing their number in Settings only gets it after the code sent to the NEW number is entered.
- Sending uses the WhatsApp Business Cloud API and an approved Authentication template (`WHATSAPP_OTP_TEMPLATE_*` in `.env.example`). Without credentials, `next dev` runs in test mode (the code is returned as `devCode` and shown on screen); in production it fails closed. Tests can point `WHATSAPP_API_BASE_URL` at a local stand-in and read the code from the captured message.
